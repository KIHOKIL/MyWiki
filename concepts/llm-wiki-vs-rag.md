# LLM Wiki와 RAG의 차이 및 구축 전략

## 1. 핵심 구분: 기술보다 "무엇을 올릴 것인가"
RAG와 Wiki 중 무엇이 더 좋은 기술인지 묻기 전에, 지식 베이스에 어떤 성격의 데이터를 넣을 것인지 정의하는 것이 우선되어야 한다.

## 2. 판단 기준 (RAG vs Wiki)
* **검색 증강 생성(RAG)이 적합한 경우:** 
  * 규정, 뉴스 등 실시간으로 데이터가 변하는 경우.
  * 답변과 함께 원문을 그대로 대조하고 확인해야 하는 경우.
* **LLM Wiki(정리본)가 적합한 경우:**
  * 이미 정제되고 정리된 지식을 바탕으로 일관된 답변을 얻고자 할 때. (안정성이 더 높음)

## 3. 개인과 회사의 환경 차이
* **개인:** 자료의 수집, 검토, 관리를 개인이 직접 수행하므로 체계가 비교적 단순해도 동작한다.
* **회사:** 공식 문서에 대한 명확한 정의, 권한 관리, 버전 관리 등 **관리 체계(거버넌스)**가 반드시 갖춰져야 한다.

## 4. 결론 및 시사점
기술적인 도구 선택보다 중요한 것은 자료를 관리하고 책임지는 체계를 설계하는 것이다. 특히, 어떤 자료를 **'넣지 않을 것인가'**를 고민하고 필터링하는 과정이 가치 있는 인사이트를 만드는 핵심이다.

## 📊 세컨드 브레인 5대 구축 방식 종합 비교

| 방식 | 핵심 메커니즘 | 장점 | 단점 |
|---|---|---|---|
| **Naive RAG** | 청크 분할 + 벡터 유사도 검색 | 빠른 MVP 구현, 단일 팩트 검색 용이 | 단편화된 맥락, 깊은 인과관계 이해 불가 |
| **[[concepts/graph-rag|Graph RAG]]** | 엔티티-관계 그래프 + 다중 홉 탐색 | 다중 문서 간 복합 연결 및 추론 강력 | 인덱싱 및 그래프 구축 토큰 비용 높음 |
| **[[concepts/agentic-rag|Agentic RAG]]** | 자율 에이전트 + 도구 호출 + 반사(Reflection) | 높은 유연성, 자체 교차 검증 및 복구 | 추론 단계 증가로 레이턴시/비용 증가 |
| **[[concepts/llm-wiki-workflow|LLM Wiki]]** | 마크다운 문서 + Git 버전 관리 + 사전 바인딩 | 명확한 휴먼 피드백 정렬, 완벽한 버전 추적 | 대규모 확장 시 수동 관리 오버헤드 |
| **[[concepts/memgpt|MemGPT]]** | OS 가상 메모리 페이징 (RAM vs Disk) | 무제한 컨텍스트 환상, 영구 세션 기억 유지 | 고성능 LLM 강제 및 정교한 프롬프트 필요 |
