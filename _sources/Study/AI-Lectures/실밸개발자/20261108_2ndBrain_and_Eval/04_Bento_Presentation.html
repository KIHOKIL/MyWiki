Part 1 · The Real Bottleneck

AI 코딩의 병목: 코드 생성 ➔ '검증(Verification)'

프롬프트를 깎지 말고, 컨텍스트와 검증을 관장하는 시스템 하네스(Harness)를 구축해야 합니다.

❌ 프롬프팅 중심 코딩의 한계

  • 코드 타이핑 병목 소멸: LLM이 1초 만에 수백 줄의 코드를 작성
  • 초대형 PR 범람: 인간 리뷰어의 뇌에 감당 불가능한 검증 부하 집중
  • 환각(Hallucination) 공포: 결과물을 믿을 수 없어 수동 대조하느라 생산성 정체
  • 컨텍스트 리셋: 매 세션마다 아키텍처 규칙을 사람이 재설명하는 비효율

🛡️ 메타의 $30,000/월 실험 교훈

  • 하재상 엔지니어의 통찰: 사내 대시보드 월 $30k API를 쓰며 절감한 원칙
  • 하네스(Harness) 전환: 룰과 툴만으로는 부족, 자동 검증 체계가 필수
  • Context Layer (2nd Brain): 컴파일러 AST 기반으로 맥락 자동 주입
  • Verification Layer (Eval): Hard Check + K-Judge로 통계적 신뢰도 확보 후 CI 머지
Part 2 · Meta Case Study

메타 실전 사례: 성능 프로파일링 10시간 ➔ 30분 단축

대규모 분산 백엔드 서비스의 지연(Latency) 트리아지를 에이전틱 하네스로 95% 단축한 비결

1. 기존의 고난도 수작업

  • 초대형 분산 백엔드 레이턴시 급증
  • 수천 개 모듈 간 상호 호출로 원인 추적 난해
  • 시니어 엔지니어가 Flame Graph와 Trace를 10시간 동안 수작업 대조

2. 하네스 3대 결합 솔루션

  • Profiling MCP: Flame Graph 수치 직접 질의
  • Senior Skill Manual: 시니어의 5단계 진단 매뉴얼을 마크다운 패키징
  • 2nd Brain Graph: 의존 함수 및 데이터 흐름 즉시 역추적

3. 성과 및 핵심 교훈

  • 진단부터 패치 제안까지 30분 만에 완료
  • 단순 Grep 검색은 90% 이상 무관한 주석/더미 반환
  • MCP 도구 + 시니어 노하우 + 코드 지도의 결합이 자율화의 핵심
Part 3 · Second Brain Architecture

컴파일러/AST 기반 Codebase Graph

Grep의 키워드 검색 한계를 극복하고, 수학적으로 100% 결정론적인 파급 반경(Blast Radius)을 계산합니다.

🕸️ 왜 단순 Grep이 아닌 AST 컴파일러인가?

  • Grep의 맹점: 키워드 검색 시 주석, 테스트 더미, 이름만 같은 무관 변수가 대량 유입되어 토큰 낭비 및 환각 유발
  • `brain build` 인덱싱: TypeScript Compiler API, Clang AST 파서를 통해 모든 함수/구조체/클래스에 고유 Symbol ID 부여
  • 방향성 엣지: CALLS, IMPORTS, WRITES_TO 관계를 엄밀하게 저장
  • BFS Hopping: 특정 함수 수정 시 파급되는 2차, 3차 영향권을 수학적으로 정밀 계산

🧠 Code Memory & Routing Rule

  • 'Why'를 복원하는 Code Memory: 그래프는 현재 구조만 알 뿐 과거 설계 의도를 모름. Git 커밋, PR 리뷰, ADR 연동
  • BM25 랭킹 채택: 일반 벡터 임베딩이 놓치는 희귀 하드웨어/엔지니어링 약어를 정확하게 매칭
  • 2원화 라우팅 규칙:
    • Fast Path: 단일 파일 로컬 수정 ➔ LLM 직접 편집 (No Brain)
    • Brain Path: 공용 인터페이스/아키텍처 수정 ➔ Graph & Memory 선행 조회 의무화
Part 4 · Verification Architecture

Eval 체계: 결정론적 Hard Check + K-Judge Majority Voting

Claude Code 시스템 프롬프트 변경 참사를 막는 2단계 검증 및 샌드박스 무균 격리 파이프라인

Stage 1: Hard Check

  • 컴파일 성공 여부 (Clang exit code == 0)
  • 정적 분석 & 린트 무결점 (Clang-Tidy)
  • 단위 테스트 통과 (Unit Test Pass)
  • 스키마 규격 일치 (JSON Schema)
  • 1개라도 실패 시 즉시 0점 탈락

Stage 2: K-Judge Voting

  • LLM-as-a-Judge 정성 평가
  • LLM 확률적 변동성(Variance) 제거
  • K=3회 독립 실행 (3인의 교수 심사 모델)
  • 2표 이상 찬성(Pass) 시에만 최종 합격
  • 아키텍처 규칙 및 예외 처리 검증

Sandbox & CI Gate

  • 무균 격리: Ground Truth 은닉, 글로벌 설정 오염 차단
  • 골든 프롬프트: 실무 전형 20~30개 시나리오 벤치마크
  • CI Gatekeeper: "CI에서 자동 실행되지 않는 Eval은 없는 것과 같다" (PR 머지 강제)
Part 5 · Maturity & Standards

메타의 Eval 성숙도 5단계 및 스킬 3대 필수 질문

감(Vibe)에 의존하는 단계에서 셀프 피드백 루프까지의 진화 단계

📈 Eval 성숙도 5단계 (Levels 0 ~ 4)

  • Level 0 (느낌 / Vibe): "어? 잘 되는 것 같은데?" (가장 위험)
  • Level 1 (단위 테스트 & 린트): 기본적인 하드 체크 자동화
  • Level 2 (오프라인 Eval): 골든 프롬프트 벤치마크 정량 점수화
  • Level 3 (CI Gatekeeper): PR 머지 전 자동 Eval 통과 의무화
  • Level 4 (Self-Improving Loop): 에이전트가 실패 사례 분석 후 프롬프트 자체 교정

🎯 스킬 개발 시 반드시 답해야 하는 3대 질문

  • 1. Triggering Accuracy (호출 정확도):
    불려야 할 때 정확히 불리고, 안 불려야 할 때 토큰을 낭비하지 않는가?
  • 2. Performance Gain (실질적 성능 향상):
    기존 Baseline 대비 작업 성공률이나 속도가 유의미하게 개선되었는가?
  • 3. Non-Regression (기존 역량 보존):
    새로운 스킬을 추가했더니 기존 기능이 망가지는 부작용이 없는가?
